# The scene editor

The scene editor is a design tool for finding, editing, previewing and saving scenes without touching JavaScript. This is how it works and what it reaches; the README's Layout section has one line for it. Moved from the README (#580).

## Index

The scene editor (#334) is a design tool that is not linked from the game: open `editor.html` to list every scene (storylets, the main characters' and captains' scenes, the hired events and the ice run) with its source file, where it plays and whether it is data or code, to search and filter them and to read one. It marks scenes the narrow build leaves out, and says where a code-written scene's text or results live inside a function.

## Text edits

For a data scene the editor has a form for the title, text, each choice's label and each result, with the shipped words beside it; a `{placeholder}` the game would not replace is flagged. It shows the changes as the text of `js/overrides.js` and never writes to the repo or a save (saving is #340).

## Preview

A data scene can also be played (#337): "Play this scene" starts a fresh test game in a frame (`editor-preview.html`, the game's own page and scripts) from a state chosen on the page (hired hand or owner, post, captain and first officer, the main characters aboard, day, credits, standing, story qualities, place), opens the scene in the game's own dialog with the unsaved edits applied, says which of its conditions fail there and which choices are shut, and lists what each choice changed. What the game stores in that frame stays in a memory that goes with it, so no real save is touched.

## Conditions and effects

For a data scene the editor also edits its conditions, and each choice's conditions, effects and `next` link (#338), with forms built at run time from the game's `CONDITIONS` and `EFFECTS` tables (`js/storylets.js`), so a key the game gains has a form at once (a box for JSON until the editor knows its kind). Each value is checked as it is typed, a field with a problem is left out of the changes, and nothing the forms write is a scene `addStorylet` would refuse. A code-written scene shows when it plays as read-only text.

## New scenes and the chain view

A scene can also be written from scratch (#339): "New scene" opens a form for its id (checked against every scene), title, text, where it plays, how it is shown, whether it only plays when another scene leads to it, its conditions, and its choices with their conditions, effects, results and links. It is a draft held to the check `addStorylet` makes, shown in the index and the preview, and written to the changes as an entry of `NEW_SCENES`. The chain view (the control beside the filters) draws a storyline's scenes as boxes with the links under them: a choice's `next`, a follow-up set going with `later` that a scene waits for with `due`, and a story stage, flag or quality a choice sets that another scene waits for. It flags a link to a scene that is not there, and a scene that only plays after a link and has none (code can lead to scenes with `chainTo`, which it cannot see). Clicking a box opens that scene.

## Save, export, import and revert

The editor keeps its edits in this browser under its own key (`maxGravity.editor.v1`), so they survive a reload, and it never writes to the repo or to the game's saves. **Export changes** downloads `js/overrides.js` whole, comments included (with no changes it is the file as it stands), to replace the file and commit. **Import a file** reads such a file as data and never runs it, lists what it would change and what it refuses, item by item with the reason, and applies the rest only when confirmed (it replaces your edits to the scenes it names). **Revert this scene** and **Revert everything** show the shipped version first and go back to it when confirmed; a scene the form does not edit (fields such as `priority`, a text of conditional parts) is kept as it is.

## The hired scenes and their ids

The hired chapter's scenes (#342) each have a stable id in one registry, `js/hiredscenes.js` (192 of them, pinned in `tests/fixtures/hired-scene-ids.json`), which the index reads. A main character's, first officer's or captain's scene can have its words edited, whether its choices are data or code: a data choice (`{ label, result, effects }`, played by `dataChoice` in `js/cast.js`) also has its effects in forms, built on five effects (`castLike`, `castFlag`, `castXp`, `captainLike`, `captainFlag`, each shape checked), and a code choice keeps its effects in code, so a result written in the editor replaces the line it returns. 61 scenes are data (#459, #460, #461): the first officers' scenes without the pivots, the main characters' meeting, intro, middle and late scenes, and the captains' secret and trouble scenes, except for the choice that rolls (Ruben's tip). A meeting scene's choices are data too: `castJoin: key` puts the person on the crew (the choice's result is what is said), `castLater: key` puts the offer off for eight days, and `when: { berths: 1 }` shuts the offer when no berth is free, with the reason "There is no free berth aboard." as `gated(needBerth)` did. A meeting plays in the preview at a port with the person not yet aboard, in an owner's game. A data choice can have a `when` (#460), shown in the editor as forms and changed through the override layer: `credits` shuts it with the reason "You have N cr; this costs M cr." as `gated(needCr(n))` did, `opinion: { who, min }` (the captain, the first officer or a main character; a new condition) shuts it with what it needs in its label, and any other condition shuts it with no reason. A named post's experience is the `gainSkill` effect.

## The captains' goodbyes

The four captains' goodbyes (#476) are data too: the goodbye is built from the captain's `goodbye` entry (`captainGoodbye`), an opening by their regard for you, a line for each of who goes with you, the secret learned, a loan repaid and the first officer, and a parting, and each of those parts is a field in the editor and a key of `parts` in a file (the lines about what the hand lived through are shared by every captain and are not edited). Its choices are data, and a choice shown only when you learned the secret has `when: { captainFlag: 'secretKnown' }` (a new condition on the hand's record); one whose condition fails is not offered. The goodbye plays in the preview. Only the pivots stay code now.

## Hired events about one person

Seven hired events about one person (`crew-ines`, `crew-tomas`, `crew-yelena`, `crew-ruben`, `crew-bexa`, `crew-pax`, `crew-cover`; #473) are data too, as `dataEvent({ ..., data: { title, text, choices } })` in `js/hiredevents.js`: a `learn` effect gives the experience and adds its line about it to the result, `{mate}` is the shipmate's first name, and two more effects (`mateLike`, `remember`) act on that shipmate. They have ids in the index, forms for their effects, words that the override layer changes, and a preview with a shipmate aboard; the other hired events stay code (#463).

## Work events, ice run scenes and the beats

The 20 work events and the 3 ice run scenes keep their words in tables that one template plays (`WORK_EVENTS` in `js/hiredeventstext.js`, `ICE_STAGES` in `js/icerun.js`), and the override layer reaches those tables (#462): by `hired:<id>` and `ice:<n>` a file can change the title, the text (an ice scene has a second opening, `text2`), each choice's label, and a choice's `result` or its `win` and `lose` lines. The editor has fields for them and plays them from a chosen state (a work event at its own post, an ice scene as the hand's post). The odds, what a win or a loss gains and costs, and the roll stay in code, so these rows have no conditions or effects to edit, and a file that names `effects`, `when` or `next` for one is refused. `tests/tablepin.test.js` pins the words the tables play. The ship fight, dead in space, the ambush and the boarding beats are reached as lines (see below); `tests/hiredpin.test.js` pins what all 164 cast and captain choices do against `tests/fixtures/hired-scene-pin.json`, so converting more of them shows it changed nothing. The plan for the rest is `docs/superpowers/plans/2026-10-09-hired-scenes-to-data.md`.

## The fights, the dock and versions

The ship fight (`scene:fight`), the ambush, dead in space and the two deck fights (`beats:repel` on our deck, `beats:assault` on hers) are edited line by line, by the name each line has; the turns, the damage and the odds stay in code. The lines both deck fights read, the abilities of each post and the orders to the crew, are one row, `beats:deck` (#795); each fight's own titles, openings, ends and memories stay in its row. The preview plays a fight row from one of the tester panel's fights (`UAT_FIGHTS` in `js/uat.js`, early or late in the chapter), picked beside the Play button: by default the one the line typed needs (the patrol for the navy's lines, `open.gun.*`, `*.gun`, `end.crippled.patrol` and `memory.navy`; the veteran corsair for the torpedo's; the pair for the consort's; our deck for the deck lines, and her deck for hers and for `beats:assault`; else the lone raider). An opening typed plays on its day, a turret is fitted when a turret line is edited, and boarding her goes straight onto her deck. What a choice changed is counted from Play, so the clicks of a fight add up: with the armor, the ship's fund, the torpedoes, each of the crew fit, hurt or dead, the hand's own hurt and the experience at each post. A function-built scene plays where its registry entry says: one at a port is played landed there, one in a burn on the way. A day ashore (`scene:day-ashore`) plays at a port as the menu with every entry the port has that day. The errand ashore (`family:errand`) is a port scene: it plays at a landing for a crew member who thinks well of you, as the errand of the culture whose line was typed last (Earth, Mars or the Belt), or the clinic's, with that person hurt, when a clinic line was. The freight agent (`scene:freight-agent`) plays the case whose line was typed (late, short, lost, or the money held back), and the side on the manifest (`scene:freight-side`) a contract from the Compact's freight office with a crew member it wants aboard (the first of the crew who is not a main character stands in, and the report says so); the close of chapter two plays the ending typed, with stand-in names that the report names. Where a moment has versions taken by the day (`text.1` and `text.2`, or `earth.1.text`, beside the line with no number), the preview moves the day to the version typed in last, the unnumbered line being the first, and the form says the days each version plays on (day 0, 3, 6... for the first). A repair line of the downtime on a burn plays for a hand at the engineer post with the armor down, since only that hand is offered the repair; the drills are an owner's and do not play for a hand. A scene the preview cannot build says so.

## How often a scene comes up

How often a scene comes up (#341): every scene shows its tier (0 the story, 1 due now, 2 drawn from the pool by weight), its weight, its cooldown where they exist, and what triggers it. A color scene (a storylet drawn by `pickStorylet`) has its weight (0 to 100, default 1), cooldown (`every`, in days) and an off switch edited in the form, as overrides; the story's, the main characters' and the captains' scenes show theirs read only with their trigger, since they are drawn by priority, by their days or by a ramp and not by weight. "How often it comes up" in the preview runs the game's real `pickHappening` on fresh test games from the chosen state (the number of games and of burns, or landings for a port scene, are set on the page) and reports how often the scene in front plays, how often a draw is quiet and events a burn, with its sample size and a range. It is a sample, not a rule of the game, and is not part of `npm test`; it counts only the draws of `pickHappening`, where `npm run soak` plays whole chapters. Story, main-character and captain scenes are not simulated. A weight that moves a scene's share of one draw is checked over many draws in `tests/distribution/frequency.test.js`.

## The override file

The scene editor's changes to the shipped words, as one object keyed by a storylet's id and then `title`, `text` and `choices` (by the choice's place in the list, each with a `label` and/or `result`). `storyletEvent` puts them in front of the shipped text; the rest of the scene is untouched. The file can also replace a scene's `when`, and a choice's `when`, `effects` and `next` (a scene id, or null for none); `pickStorylet` and `storyletEvent` read them through `sceneView`, and `cleanOverrides` holds them to the check `addStorylet` makes (`storyletProblems`), leaving out together all of a scene's changes of that kind that it would refuse. A color scene can also take `weight`, `every` (days before it can come round again) and `off: true`, read by `pickStorylet` through `sceneRate` (a scene drawn by priority or by its days has none, and the file is refused item by item if it names one). Empty means the shipped game. `NEW_SCENES` in the same file is a list of whole scenes written in the editor; `useNewScenes` adds them through `addStorylet` when the first game starts (one it would refuse is logged and left out), and again whenever the editor's preview asks. An unknown id or a value that is not text is left out with one console warning, and an override's text is escaped where it is shown.
